# ElementWar 功能工作流与完成标准

本文件是大型任务流程、验证等级和 Definition of Done 的唯一维护来源。

## 0. 短指令入口与自适应流程

用户可以使用以下短指令，无需在每个对话重复项目规则：

- `继续下一阶段`：读取 [`DevelopmentRoadmap.md`](DevelopmentRoadmap.md) 中唯一标记为 `Next` 的任务及其路线细则，核对实时仓库后进入只读检查与集中澄清。
- `开始功能：<名称或任务 ID>`：定位指定路线任务，检查依赖；前置未完成时报告缺口，不静默跨越。
- `按已批准 Feature Spec 继续实施`：只在 Feature Spec 已批准且实时范围没有高影响漂移时恢复实施。

短指令不等于预先批准未知方案。大型任务仍需在只读检查后给出一次精简的目标、非目标、范围、方案、风险和验收总结，并等待明确实施授权。

质量门槛保持稳定，任务组织按风险适配：

| 类型 | 典型情况 | 推荐组织 |
|---|---|---|
| 局部闭环 | 单一职责、无公共接口或序列化变化 | 同一任务检查、实施、精确验证和自审 |
| 标准垂直切片 | 跨少量系统但行为与依赖明确 | 一个 Feature Spec 持续到目标验证等级；是否另开审查按风险决定 |
| 高风险迁移 | 公共契约、状态所有权、scene/prefab、序列化、物理/计时或发布边界 | 独立设计/授权门，实施后优先独立只读审查和更高证据等级 |
| 探索任务 | 关键技术或现有缺陷尚无法证实 | 先做有时间上限的只读审计、特征测试或隔离原型，再决定生产方案 |

不以“一个任务完成”或“必须拆任务”为目标；以尽早暴露高风险、减少无效返工并获得可信证据为目标。

## 1. 建立行为契约

以 `Docs/Features/TEMPLATE.md` 为模板，明确：

- 玩家或开发者可观察目标。
- 当前已验证行为与调用链。
- 非目标、允许范围和禁止范围。
- 配置、运行时状态和事件所有者。
- 生命周期、兼容性、性能和回滚。
- 自动化与人工验收标准。

## 2. 只读检查与澄清

AI 先从仓库确认事实，不把推断当结论。只询问会影响范围、行为、接口、验收或技术取舍的问题。澄清后总结理解，并等待“开始实施”或同等明确授权。

## 3. 最小垂直切片

每次实现一个完整、可观察、可验证的行为链。保持程序集边界和唯一事实源，不顺手清理旧架构或无关代码。每个切片后检查 scoped diff，并运行最低成本的相关验证。

## 4. 文档维护与精简

- 文档只保留当前有效事实、行为契约、范围、验收、运行方式、最终证据和维护约束；非适用内容直接省略。
- Feature Spec 关闭后删除实施时间线、已被替代的方案、重复授权，以及可由 Git 历史或原始日志恢复的过程细节。
- 同一事实只保留一个权威来源；其他文档使用链接或路径引用，不复制正文，发现冲突时先修正权威来源。
- 修改文档时，默认同时检查并更新所有受影响的总览、导航、交叉引用和派生摘要；只有用户明确限制为单一文档时才停止联动，且不得借同步扩大到无关内容。
- 必须保留的历史压缩为一条结论和对应证据路径，不在当前契约中重演过程。
- 不为填满模板而新增无实际信息的章节、占位段落或重复清单；模板章节仅在适用且有内容时保留。
- 单份长期维护文档超过 300 个非空行，或同时承载多个通常会被独立读取的子系统时，必须按稳定职责拆分；原文档只保留导航和跨域约束，拆分后不得复制正文。
- 读取设计资料时先用总览定位，再只加载与当前任务直接相关的细则；不得把“可能有用”作为预先加载全部设计文档的理由。
- 功能收口与后续维护均检查文档 scoped diff，确保最终证据仍可定位，且文档没有重新累积过程记录。
- 开发顺序、任务状态和依赖只在 [`DevelopmentRoadmap.md`](DevelopmentRoadmap.md) 及其路线细则中维护。设计文档描述目标行为，Feature Spec 描述获批切片，三者不得相互复制整段正文。
- 路线始终只能有一个 `Next`。功能收口时更新原任务状态、证据链接和后续解锁项；需要改变顺序时记录依赖或风险理由，不静默按旧对话改序。

## 5. 验证等级

| 等级 | 证据 | 含义 |
|---|---|---|
| Implemented | 代码/diff | 已实现，尚不能称完成 |
| Fast Verified | 精确测试 + EditMode | 切片验证通过 |
| Full Verified | EditMode + PlayMode + Windows64 构建 | 可进入人工验收 |
| Accepted | Full 证据 + 主线场景人工验收 + 文档闭环 | 功能完成 |

测试数为 0、缺少 XML、非零退出码或缺少预期 Player 都视为失败。跳过的检查写成“未运行”。具体测试/构建选择在需要验证时读取 skill 的 `references/verification-matrix.md`。

## 6. 风险驱动的独立只读审查

以下任一情况存在时，优先考虑另开 Codex 任务，仅基于批准后的 Feature Spec、完整 diff 和原始验证证据独立检查：

- 公共接口、状态所有权、程序集或组合根发生变化。
- scene/prefab、ScriptableObject、Input Action 或其他序列化数据迁移。
- 物理、帧时序、异步生命周期、对象池复用或高扩散事件链。
- 变更规模使实施者自审难以保持独立，或准备进入发布候选版本。
- 测试大量依赖反射、动态装配、替身或未加载真实资产。

审查重点：

- 行为是否满足验收。
- 生命周期函数、事件订阅、禁用/死亡/重置和对象池复用。
- 架构、公共接口和序列化边界。
- 测试是否证明可观察行为，而非只绑定实现细节。
- 完成声明是否有对应证据。

审查发现必须分类：

| 分类 | 默认处理 |
|---|---|
| 已确认缺陷 | 阻断当前收口；回到获批范围内修复并重跑受影响验证 |
| 违反验收 | 阻断当前收口；修复实现或由用户重新批准行为契约 |
| 证据缺口 | 下调完成等级或补充证据；除非同时证明缺陷，否则不自动要求改生产代码 |
| 可选增强 | 记录到路线或后续 Feature Spec，不扩大当前范围 |

没有上述风险、差异局部且自动化直接覆盖生产行为时，可以由同一任务完成最终自审，不为流程形式重复开启审查。

## 7. Definition of Done

- [ ] 目标、非目标、范围、方案和可观察验收已经批准。
- [ ] 实现没有超出授权，也没有吸收用户无关改动。
- [ ] 依赖方向、状态所有权、生命周期和序列化影响已处理。
- [ ] 相关自动化测试数量大于 0 且通过。
- [ ] 当前里程碑要求的 Fast/Full 验证通过。
- [ ] 玩家可见行为已在主线场景人工验收。
- [ ] 有性能目标时保留代表性 Player 数据；不编造提升数字。
- [ ] Feature Spec/ADR 与最终行为一致。
- [ ] 属于开发路线的任务已同步状态、证据、解锁项和新的唯一 `Next`。
- [ ] 最终报告列出命令、结果、证据、未运行项、风险和回滚。

仅“代码已写”或“编译通过”不满足 Definition of Done。
