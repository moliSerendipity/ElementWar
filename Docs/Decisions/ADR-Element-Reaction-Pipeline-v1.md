# ADR：元素反应表、命中顺序与目标侧原子事务 v1

- 状态：Superseded
- 日期：2026-08-22
- 负责人：Codex / 项目维护者
- 关联 Feature Spec：[`ElementReactionPipelineV1.md`](../Features/ElementReactionPipelineV1.md)
- 取代决策：[`ADR-Element-Pipeline-Simplification-v1.md`](ADR-Element-Pipeline-Simplification-v1.md)

> 本文保留 ELM-030 首次实现时的历史取舍与验证记录。反应表资产、批次包装请求、Origin、基准伤害和结果拒绝矩阵不再是当前契约；现行实现以取代决策和 Feature Spec 为准。

## 背景

`ELM-020` 已让目标 `ElementAttachmentRuntime` 在异元素到达时返回已有附着版本和触发请求，但尚无反应表、同命中顺序、反应级去重或归因结果。首版同一次命中可能同时包含弹药元素与技能元素；一旦其中一个触发反应，后续应用必须停止。真实武器来源尚未接入，因此本决策只关闭通用事务，不提前实现 `WPN-010` 或具体反应输出。

## 决策因素

- 玩家与开发者结果：元素先后顺序不改变反应类型；同一攻击/目标只触发一次；消费、归因和剩余附着确定可解释。
- 架构约束：Definition 保存不可变映射，目标 Runtime 保存可变状态；Gameplay 不依赖 Presentation；伤害与元素仍为并列输出。
- 生命周期：迟到版本、重复 Collider、死亡、禁用和对象复用不能误清当前状态或重复反应。
- 完成风险：公共契约应足以支持 `WPN-010` 和 `ELM-040`，但不建立无消费者事件、输出框架或新组合根。

## 备选方案

### 方案 A：由每个武器/技能调用者逐个处理元素和反应

- 做法：生产者自行决定弹药/技能顺序，看到 `ReactionRequired` 后查表并消费。
- 优点：新增公共类型较少。
- 成本与风险：顺序、停止规则、版本消费、来源间隔和去重会散落到多个生产者，容易形成不同语义。

### 方案 B：精简批次管线 + 目标侧原子提交

- 做法：一个管线请求保存可选弹药/技能应用、基准伤害和派生标记；静态管线统一预检与顺序；目标 Runtime 原子提交消费和去重。
- 优点：生产者只有一个入口，状态仍由现有目标所有者维护；无需新增组件、单例或逐帧驱动。
- 成本与风险：新增公共请求/结果契约，并把默认 Registry 精确迁移到单一反应表资产。

### 方案 C：新增全局反应服务持有目标状态和执行去重

- 做法：全局服务统一保存所有目标附着、反应和执行记录。
- 优点：可以集中查表和调度。
- 成本与风险：与 `ElementAttachmentRuntime` 形成平行状态源，引入组合根和销毁/复用同步问题，超出当前切片。

## 决策

选择方案 B。四元素六反应使用一个 Definition 表资产，以无序元素对查询；完整结构与唯一性检查只在 Bootstrap 配置校验阶段执行，运行时查询不重复扫描整张表。Gameplay 管线固定弹药先、技能后，预检共同执行/目标/时间并拒绝 ReactionDerived；反应成功后由目标 Runtime 在一次事务中登记第二来源间隔、登记执行去重并版本化消费已有附着。

结果直接返回给未来生产消费者，保留已有附着、触发请求、反应类型、目标/执行、第二来源归因和触发基准伤害。本阶段不发布反应事件；`ELM-040` 出现真实权威输出与表现消费者时再按实际事件语义决定。

## 后果

正面影响：

- 同一命中的顺序和停止规则只有一个实现点，重复调用不会在空槽重新留下元素。
- 反应映射、运行时消费和归因分责明确；迟到消费者不能清除刷新后的附着。
- 不新增 MonoBehaviour、Update、单例或第二状态容器，未来武器/技能只需建立请求并调用管线。

代价与限制：

- 默认 Registry 必须始终提供启用且结构完整的六对反应表。
- 当前仍无玩家可见反应；真实步枪输入、反应输出、反馈事件和数值分别留给后续路线任务。
- 首版请求只表达弹药与技能两个固定阶段；若未来同一命中需要更多有序来源，必须重新评估契约而不是静默依赖集合顺序。

## 迁移与回滚

- 增量步骤：新增 Definition 表和资产；新增精简 Gameplay 请求/结果/管线；扩展目标 Runtime 原子事务；迁移测试；最后同步权威文档和路线。
- 序列化/API 兼容性：只向默认 Registry 新增一个表引用，不修改 scene/prefab/asmdef；新增 Unity 资源保留独立 `.meta` 和 GUID。现有单请求 Resolver 作为管线低层实现保留，不成为生产入口。
- 回滚单位：反应表与 Registry、管线契约、目标事务、测试和文档整体回滚。
- 对旧架构的影响：无；Legacy/Lua 与旧场景保持只读。

- 构建证据：Windows64 未运行；本 ADR 不声明 Full Verified 或 Accepted。
- 性能证据：没有性能提升声明；六项表使用固定小规模线性查找，反应执行集合随目标生命周期清理。
