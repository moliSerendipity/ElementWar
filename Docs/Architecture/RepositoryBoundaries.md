# Repository Boundaries

只在任务涉及主线目录、Legacy、共享资源、第三方内容或迁移边界时读取。

## 当前主线

当前新架构代码以以下程序集和目录为主：

```
Assets/Game/Foundation
Assets/Game/Definition
Assets/Game/Gameplay
Assets/Game/Presentation
Assets/Game/Editor
```

依赖方向以 `../Architecture.md` 为准。

除非任务明确涉及旧系统迁移，不从 Legacy 反向复制旧架构模式进入新主线。

## Legacy

旧实现只证明仓库当前存在这种代码，不自动构成：

- 新功能必须兼容的公共契约；
- 必须继续维护的状态所有权；
- 必须复用的抽象；
- 必须保留的序列化结构；
- 新代码必须遵循的目录和依赖方式。

只有以下情况才需要主动兼容 Legacy：

1. 当前生产场景、prefab、ScriptableObject 或运行入口仍直接依赖它；
2. 当前任务明确要求迁移期间共存；
3. 删除或改变它会破坏已经确认需要保留的用户数据、资源引用或运行行为。

如果不存在上述依据，不为了“以后可能迁移”提前增加 Adapter、Facade、双写状态或兼容分支。

## 修改边界

- 当前任务不依赖旧架构时不修改；若完成当前需求必须触及其行为，可在已授权范围内做最小必要修改。迁移、替换或清理属于 Full。
- 用户已有未提交修改不属于当前任务时，不格式化、不重排、不吸收进本次变更。
- 不顺手修复附近无关问题；发现后在最终报告中指出即可。
- 第三方 Package、Plugin、SDK 和导入源码默认只读。若问题确实来自第三方，优先在项目侧建立最薄适配层，而不是直接修改第三方代码。
- 不修改 `Library`、`Temp`、`Logs`、`obj`、`.vs`、自动生成的 `.sln/.csproj`。
- 不自动执行 Git reset、clean、checkout、stash、commit、push、rebase 或历史重写。

## Unity 序列化资源

以下修改视为序列化边界，而不是普通文本编辑：

- scene；
- prefab；
- ScriptableObject 资产；
- Material；
- Animator Controller；
- Animation Clip；
- Input Action；
- Project Settings；
- 其他带 GUID 引用的 Unity 资产。

处理这些资源时：

1. 尽量通过 Unity 正常序列化路径修改，不批量重写 Unity YAML；
2. 新增、移动、重命名、删除资源，或改变对象引用、GUID、结构/序列化契约时，检查受影响引用和 `.meta` / GUID；
3. 普通标量配置调整只检查直接受影响对象，不做仓库级引用扫描。

只修改现有 `.cs` 内容无需检查未变化的 `.meta`；新增、移动、重命名或删除脚本时再维护对应 `.meta` / GUID。新增资源时确认 `.meta` 正确生成并进入版本控制。

## 共享资源

共享资源的存在不表示所有系统都可以直接依赖。

复用前先确认：

- 资源是否属于当前主线；
- 是否会造成新的程序集反向依赖；
- 是否含旧系统状态或行为假设；
- 是否只是视觉/配置资产，可以通过现有 Definition/Presentation 边界引用；
- 是否需要迁移，而不是直接在新旧系统之间建立永久耦合。

如果只是为了减少几行代码而引入跨层依赖，不复用。

## 已知边界的处理原则

发现当前代码违反架构方向时：

- 当前任务不依赖该问题：记录，不扩大范围。
- 当前任务可以在不新增债务的情况下绕开：使用现有正确边界。
- 当前任务必须继续依赖该问题才能完成：明确指出，并选择最小局部处理。
- 需要改变状态所有权、程序集方向或长期迁移策略：升级为 Full Workflow，并视情况创建 ADR。

不要因为发现一个旧架构问题，就自动把当前功能变成仓库级重构。
