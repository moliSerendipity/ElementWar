# ElementWar 开发路由

先遵守根 `AGENTS.md`；只有 Full 读取 `Docs/Workflow.md`。

## 等级

| 等级 | 条件 | 默认动作 |
|---|---|---|
| Fast | 需求明确，沿用现有契约，无高影响边界 | 直接实施；读直接代码/调用者/测试；不建 Spec/ADR |
| Standard | 跨现有系统，但所有权、公共契约和序列化边界已确定 | 直接实施；按职责补读最少 Architecture/Design；默认不建 Spec/ADR |
| Full | 状态所有者、跨模块公共契约、asmdef/依赖方向、序列化契约或共享 scene/prefab 结构迁移、Legacy 收敛、发布级性能/兼容性，或多个方案明显改变行为/接口/验收 | 读 Workflow；只确认未决高影响选择；按需建 Spec/ADR |

跨文件、新功能和文件数量不决定等级；只有实际触发 Full 条件才升级。

## 上下文

1. 按职责取最少事实：实现读代码，所有权/边界读相关 Architecture，玩法读相关 Design，范围只读当前 Roadmap task；先搜符号，再读定义、直接调用者和最相关测试。
2. Standard 在开始实施前应尽量把**本任务新增调查上下文**控制在约 40k token 内；已确认入口、权威所有者、直接消费者、现有契约和测试接缝后，停止横向扩展调查。确有未决设计或调用链证据缺口时才继续读取，并说明缺口。
3. 约 200 行以上源码禁止默认全文读取：先定位 symbol，再读目标方法/类型附近区间；只有跨区控制流确实需要时扩展。已读且未变化的区间不得重复读取，多个区间不得无意义重叠。
4. `继续下一阶段` 只读唯一 `Next` 和对应任务块；`DevelopmentRoadmap.md` 已存在唯一 `Next` 时，不查询 Codex Memory/旧会话来重新确定路线。Done 依赖以当前代码/Architecture 为契约来源。
5. 历史 Feature/Superseded ADR 只在追溯证据或决策原因时读取，其 `Verified / Accepted` 仅代表记录版本，不证明当前 HEAD。diff、设计、验证和性能资料均按当前任务缩小范围。

## 工具输出

- 搜索采用“两阶段”：先用 `rg -l` / 文件名 / symbol 定位，再只在少量候选文件内读取上下文；不要首轮同时把 Docs、Scripts、Tests 的大量匹配正文全部输出。
- 完整 Unity/构建/Test Runner 日志写文件；上下文只留退出码、数量摘要、失败项和相关错误区间。大型 XML/JSON/YAML/scene/prefab 先定位目标字段、对象或 GUID，禁止已知目标字段时全文打印。
- 单次输出预计超过约 150～200 行时必须过滤、分段或改成摘要；若工具支持输出 token 限制，常规调用优先控制在约 8k token 以内，超过约 12k token 需要明确原因。任何输出发生 `truncated` 都视为查询过宽，下一次必须缩小范围，不能把截断当作正常调查方式。
- diff 先看 `--stat` / `--name-only` 再看 scoped diff；修改后不默认全文重读，也不在收口阶段重新搜索已确认的全部 symbol。
- 长进程不高频轮询同一状态。若 Agent 自己启动的验证被外部许可/系统弹窗阻塞，先确认无有效测试输出，再终止该进程并改用仓库已知验证路径；不要仅为关闭外部弹窗加载大型 Computer Use/浏览器上下文。

## 复杂度

默认实现当前验收所需的最直接方案。Request/Result/RejectionReason、新 Event、缓存/字典、平行状态、Target/Lifecycle ID、去重集合、生命周期包装、策略/工厂/通用接口都不是默认模板。

新增复杂度必须有当前证据：消费者需要；合法路径存在具体失败；任务明确要求；或不现在处理会造成已确定的 API/序列化迁移或重复实现。Roadmap、未来需求、其他组件已有结构或“更健壮”不能单独作为依据。

已由单一边界保证的不变量不重复校验；当前调用链不存在的故障模式不设计防线。详细代码注释按 `Docs/CodingStandards.md` 保留，不视为设计复杂度。

## 执行

1. 定位入口、权威所有者、直接消费者和相关测试；达到实施所需事实后立即停止调查。
2. 完成最小可观察行为链，不顺手扩范围、清理无关旧架构或预埋未来框架。
3. **完整验证前先做一次静态自审并冻结行为代码**：检查不必要状态/序列化、明显契约遗漏和 scoped diff；能在这里发现的问题不要留到测试后再改。
4. 从最低成本的相关验证开始，按实际行为风险选择足够证据；验证种类不由 Fast / Standard / Full 决定。验证通过后，只有行为代码、序列化元数据/契约或测试逻辑变化才使相关运行时证据失效；纯注释、Markdown、格式和不影响执行结果的文本修改不要求重跑运行时验证。
5. 用 scoped diff 收口，只同步当前事实、路线状态和证据；收口只检查本次变化，不重复做已完成的仓库级调查。最终报告只写实际修改、验证、未运行项和真实剩余风险。
6. 仓库是跨任务记忆，聊天上下文不是；下一任务应能从当前代码、Architecture/Design、Roadmap 和 Git 恢复。
